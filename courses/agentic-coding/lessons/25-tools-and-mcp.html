    Building block #4, in depth

    Tools & Connections (MCP)

    Your agent can only reason about what it can reach. Tools and connections are how it stops guessing about the outside world and starts reading and acting on it directly.

    Giving the agent arms, not just a brain

    By default, an agent only knows what's in the codebase in front of it and whatever you type into the conversation. Ask it what a ticket says, what real users are actually doing, or what's currently sitting in a database table, and without a connection to those systems, it can only guess — or ask you to paste the answer in yourself.

    A tool connection closes that gap. It wires the agent directly into an external system — a ticket tracker, a database, an analytics platform, the open web — so it can read (and sometimes write) real data instead of working from secondhand descriptions. Think of it as giving the agent arms to reach outside its own sandbox.

    MCP: one standard, many connections

    Wiring up a new external system used to mean custom, one-off integration work for every single tool. The Model Context Protocol (MCP) fixes that by giving agents and tools a single shared way to talk to each other — a common connector, the same idea as a universal port that many different devices can plug into. Once a system exposes an MCP server, any MCP-capable agent can connect to it the same way.

    You can read the open standard itself at modelcontextprotocol.io. You don't need to memorize the protocol's internals — the useful takeaway is simpler: MCP is why "connect my agent to my ticket tracker" is now a small, repeatable setup step instead of a custom project.

    Setting one up is usually simple Most platforms that offer an MCP server publish straightforward setup docs. You typically don't need to hand-write the integration — you can often just point your agent at the docs and have it configure the connection and handle authentication for you.

    What this looks like in practice

    A few concrete, beginner-friendly examples of what a connection actually buys you:

    Reading a ticket

    Instead of copy-pasting a ticket's description and comments into the conversation, the agent fetches it directly from your tracker by its ID — always current, never stale.

    Querying usage data

    Ask the agent to check what a product-analytics platform actually shows about how a feature is used, instead of guessing from a hunch — real numbers instead of assumptions.

    Checking a database

    The agent can query a database directly to see the actual shape or contents of your data, rather than inferring it from code that might be out of date.

    Reading documentation

    Pull a requirements doc, a design page, or a spec straight from wherever your team keeps it, instead of relying on someone's memory of what it said.

    The context problem, and the fix

    Connections used to carry a real hidden cost. Attaching a server dumped the name and the full description of every tool it exposes into the context window at the start of every session. Each description is only a couple of hundred tokens — but a single ticket-tracker server can expose forty tools, and some expose eighty. A handful of connections could cost tens of thousands of tokens before you typed a word: an extremely bloated rules file you never wrote.

    The fix, now standard in the major agents, is tool search. The agent keeps the cheap part — which servers are connected, and the names of their tools — and defers the descriptions. When a request actually needs a platform, it searches its tools by keyword, pulls the full descriptions for the few that look relevant, and searches again if it guessed wrong. Forty tools now cost you effectively nothing until one gets used.

    You've seen this shape twice already A tiny always-on index, the bulk deferred until something reaches for it. That's progressive disclosure for skills (Lesson 23), on-demand context for rules (Lesson 22), and tool search for connections. Three surfaces, one idea — worth treating as a general principle rather than a feature of any one of them.
    Or hand the connection to a specialist There's a second fix worth knowing, and it combines two building blocks: give the connection to a subagent instead of to your main session. The tool descriptions and — more importantly — the heavy results those tools return both stay inside the specialist's own context, and what comes back to you is its summary. An analytics query that returns three hundred rows costs your main session a paragraph. It also gives you somewhere natural to write down how you want that platform used, rather than hoping the main agent works it out mid-task.

    What you're trusting when you connect one

    A connection hands your agent a set of tools written by someone else, and the tool descriptions are instructions your agent reads. If it's the first-party server of a platform you already pay for, there's little to think about. If you're being adventurous with a server whose author you don't know, three risks are worth naming:

    RiskWhat it looks like
    Tool poisoningMalicious instructions hidden in a tool's description — say, one that tries to get the agent to send an API key somewhere.
    The rug pullA server that's benign when you audit it and turns hostile in a later version. The capability you rely on can change underneath you.
    ShadowingA rogue tool that overrides or impersonates a trusted one, so what you see isn't what actually ran.
    The mitigation is boring on purpose Use the official first-party server for platforms you already trust, and all three problems mostly go away. If you do run something third-party: audit it, pin the version, narrow the authentication scopes, and give the agent read-only tools where you can.

    The other way to give an agent arms

    MCP isn't the only route. Your agent can already run terminal commands, which means it can drive any command-line tool you have installed — and a skill can teach it which commands exist and how you want them used. The CLI is the arm; the skill is the instructions for the arm.

    A connection is simpler

    The tool is the arm, and it arrives with its own description, authentication, and permissions — a curated set of interactions designed by the people who know that platform best. No companion skill needed.

    A skill plus a CLI is more flexible

    You get every command the tool offers rather than a curated subset, and the skill is tuned to your workflow rather than someone else's.

    The working rule of thumb: connections for external platforms, a skill plus a CLI for things running on your own machine — while accepting the line blurs. And you use more CLIs than you probably realize: your package manager is one, and it could carry a skill.

    Connections are optional, and added when they earn their place

    You don't need every connection on day one. Add a tool connection when a real, recurring need shows up — you keep manually pasting ticket text in, or you keep wishing the agent could just check the data itself. That mirrors the broader lesson from Lesson 6: rules and skills are where you start, and the remaining blocks, including connections, tend to get added once you actually feel the friction they solve.

    You keep doing this by handConnection that removes it
    Copy-pasting ticket details into the conversationA connection to your ticket tracker
    Manually checking a dashboard before answering "is this used?"A connection to your analytics platform
    Running the same lookup query yourselfA connection to your database

    What problem does MCP actually solve?

    Without any tool connections, how does an agent answer a question about a live ticket or a database?

    The one thing to remember

    Tool connections give your agent arms to reach real external systems, and MCP is the common standard that makes wiring one up simple. Add a connection when you notice yourself feeding it the same outside information by hand, over and over.
