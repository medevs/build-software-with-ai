    Building block #3, in depth

    Subagents

    A subagent is a specialist you can hand a heavy job to — with its own separate context — so its digging doesn't clutter the conversation you're actually trying to get work done in.

    A worker with its own workspace

    Your main agent has one context window: everything you've told it, everything it's read, everything it's tried so far, all sitting in the same working memory. That's fine for a normal task. It gets crowded fast when the job is heavy — exploring a large unfamiliar area of the codebase, digging through many files looking for one answer, or critically reviewing a finished change.

    A subagent solves this by being a separate specialist with its own context and its own tools. You delegate it one focused job. It goes off, does the heavy digging entirely in its own workspace, and hands back only a tight summary — the answer, not the messy trail of files and dead ends it took to get there. Your main conversation stays clean, exactly as it was before you delegated.

    The core payoff A subagent's isolated context is what makes it useful. All the noise of a big search or a deep review happens somewhere else — you only ever see the conclusion.

    Where subagents pay off first

    Two situations come up constantly once you start looking for them:

    Splitting up a big exploration

    On a large, unfamiliar codebase, one agent trying to understand everything at once runs out of room. Fan the exploration out across several subagents, each covering a different slice, and have them report back short summaries you can act on.

    A fresh set of eyes for review

    The agent that wrote a change is a bad judge of that same change — it's primed to think its own work is fine. A subagent with no memory of writing the code has no such bias, so it makes a far more honest reviewer.

    The classic example: a code-reviewer subagent

    The clearest instance of this pattern is a subagent whose only job is to be critical. After a change is implemented, instead of asking the same agent that wrote the code "was that good?", you hand it to a separate reviewer subagent — one with a fresh context and instructions to look hard for problems.

    This connects directly to the review step covered back in Lesson 13: the agent proving its own code runs is one kind of check. Having a separate, unbiased reviewer judge whether the code is well built is a different, harder-to-fake kind of check — and it only works because the reviewer isn't the same mind that wrote the code in the first place. You wouldn't want a student grading their own homework; the same logic applies here.

    The isolation cuts both ways

    Nothing is shared. The prompt the main agent writes is literally everything the subagent knows, and the summary it sends back is everything the main agent ever sees. You never talk to the subagent yourself — the main agent is always in the middle. So every delegation has two lossy handoffs: an under-specified task means the subagent misses something, and a finding left out of the summary is gone for good, because there's no transcript for the main agent to go back to.

    That's also why the standing advice is to use subagents for research rather than for writing code. Parallel subagents can't talk to each other, so several of them editing the same codebase at once is a recipe for collisions.

    What you actually tune: the four levers

    Writing a good subagent isn't mysterious once you know which knobs exist. There are four, and they exist to fight exactly the information loss above.

    Purpose

    What it's for, and when the main agent should reach for it. This is the part that's always loaded, so getting it wrong means the subagent fires when it shouldn't — or never fires at all.

    Dispatch

    How the main agent should prompt it. The most optional of the four; agents have got good at this on their own. Reach for it when a subagent misbehaves.

    Process

    The step-by-step and the behaviour — conventions plus procedure, scoped to one worker. It's rules and skills combined, for a single specialist.

    Output

    How it distils what it found. The king lever. Don't leave the shape to chance — specify it.

    Why output is the one to labour over The subagent has just done an enormous amount of work and has to compress it into something small. Dumping its logs would defeat the entire point of isolating it; deciding what actually matters is genuinely hard. A well-written reviewer subagent can spend a third of its instructions on the output format alone.
    A simple way to decide Ask yourself: is this job big enough, or sensitive enough to bias, that I'd want it done somewhere separate from my main conversation? If yes, that's a job for a subagent.

    Exploring a large, unfamiliar codebaseSplits the digging across several isolated contexts instead of overloading one.

    A small, quick task you'll do onceNot worth delegating — just do it directly in the main conversation.

    The one thing to remember

    Hand heavy, isolated, or bias-sensitive jobs to a subagent — a fresh-eyes code reviewer is the clearest example — and your main conversation stays clean. The rest is just recognizing when a job is big enough to deserve its own workspace.
