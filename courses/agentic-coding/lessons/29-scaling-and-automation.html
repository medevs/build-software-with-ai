    Move the loop off your screen

    Scaling & Automation

    Chain the steps, move the loop off your screen — and find the point where more automation stops making things better.

    From "I run the loop" to "the loop runs"

    Earlier in the course you learned to run one core loop at a time, then to run several loops in parallel using isolated copies of your codebase. That's already a big jump in throughput — but it still requires you, at a keyboard, starting and watching each one. The next stage of scaling asks a different question: which of these loops could run without you present at all?

    A surprising number can. If a piece of work is well-scoped, has clear rules to follow, and has a way to check itself when it's done, it doesn't strictly need a human staring at the terminal while it runs. It needs a trigger, a place to run, and a way to report back.

    The rule for deciding Reliability earns autonomy. You don't grant a loop independence because it would be convenient — you grant it because that loop has already proven, with you watching, that it does the right thing. Every scaling decision in this lesson is really the same question asked about a different loop: has this one earned it yet?

    First, chaining: steps that hand each other work

    Before a loop can run without you, its steps have to hand off to each other without you. That's all a chain is — no clever construct. One step writes something down; the next step reads it and does the next piece of work. Investigate writes what it found; the fix step reads that and changes the code; the review step reads the change and writes findings.

    Which gives you a precise definition of the thing you've been doing by hand all course: a gate is simply a place where you read the hand-off before passing it on. Nothing about automating a chain removes your ability to stand in the middle of it. You decide which hand-offs you read.

    Which raises the question of how small the steps should be. Cut the chain finely and each step becomes gateable (you can stand at any boundary), measurable (you can see which step is the weak one), swappable (you can replace one without touching the rest), and composable (the same step joins a different chain). Note what isn't on that list: the model's ability to cope. You're not chopping the work up because the agent can't hold it — you're chopping it up so you can inspect, measure, and rearrange it.

    Five ways to chain — and none of them is the standard yet

    Here's something worth noticing about the state of the field. Nearly everything else in your context layer has settled on a shape: rules became plain text files, reusable workflows became a named folder with instructions in it, guardrails became small scripts wired to lifecycle events. Composition didn't. There is no standard way to chain steps together, and several competing shapes each have tens of thousands of users.

    How the hand-off happensWhat it looks like
    Through a fileEach step writes an artifact; the next step reads it. You already own this one — it needs nothing new.
    A non-interactive callYour agent run as a one-shot command that takes a prompt and returns a result, driven by a script.
    An agent libraryThe same agent as a library inside your own program, so you get real objects and callbacks instead of parsing output.
    Guardrails that interceptA hook chains by interception rather than sequence: the next step fires because something happened, not because something called it.
    A pipeline triggerThe same non-interactive call, started by a repository event instead of by you.

    A workflow engine is the sixth answer: the hand-offs described as a graph, with the plumbing taken out of your hands. Which of the six you pick matters far less than you'd think — so don't learn one syntax. Learn the properties that any of them can give you: gates you can add and remove, artifacts that carry state across every boundary, one job per context, loops with a hard stop and an objective signal, and a written record of what got decided. If a mechanism gives you those five, it's fine.

    You're not going to write this by hand Nobody hand-writes chain scripts or guardrails any more — you describe the chain to your agent and let it build it. So the skill worth practising isn't syntax, it's the briefing: which steps, in what order, what each one hands the next, and where you want to be asked. Get that clear and the mechanism becomes an implementation detail you can swap later.

    Long chains decay, and you won't feel it coming

    Now the number that governs every automation decision you'll make. It's just multiplication.

    The failure also isn't gradual. Push agents to longer and longer runs and you don't get a gentle slope; you get something that holds up fine and then falls off a cliff. Practically, that means you will not feel it coming — which is an argument for gates rather than vigilance.

    So the structural answer is not a longer chain with more care in it. Don't run one long chain — run a short one, many times. Break the plan into tasks and loop plan → implement → review over each one, so every task is checked before the next is built on top of it. In practice most people hand over somewhat more than one task at a time and accept slightly worse accuracy for a lot less overhead. That's a preference, and knowing why the short loop is better is what lets you choose your own number instead of guessing.

    So where do you belong in your own loop?

    If you can't chain forever, the question becomes where you stand. The honest answer from people whose systems drive most of their day-to-day development is remarkably consistent: a lot of time planning, some time reviewing, and everything in between automated. The two ends stay human; the middle doesn't.

    That should sound familiar — it's the division of labour this course started with, and it holds up under the pressure of people who are free to automate anything they like. It also flips the question you've probably been asking. If you run each stage by hand, then every boundary is already a gate. So the real question isn't "where do I add gates?" It's which boundaries have earned being removed?

    And there's a mechanical answer to when a boundary has earned it, which beats waiting to feel brave. A gate is a teacher. Every time it shows you what the agent proposed and you choose something else, you've learned something specific about the gap between its judgment and yours — so put that in the prompt. Tell it the reasoning you actually use. Do that a few times and its proposals start matching what you'd have picked anyway. The gate comes out when it stops surprising you, not when you're tired of it. And the move is reversible: it was one sentence, so you can put it back.

    Make gate removal a decision, not a mood Keep a standing-decisions log: the calls you've already made, each with a scope. When the chain reaches a gate, that list is what it checks. Covered by a standing decision? Act, and record that it acted automatically. Not covered? Stop and ask — and your answer becomes the next standing decision. Without the log, gates quietly disappear because you got bored of them. With it, every removal is something you can read, argue with, and hand to somebody else. And when the run genuinely has to interrupt you, escalate a digest, not a dump: what happened in two lines, what needs deciding, the recommendation and its risk.

    And be clear about what success looks like here, because it isn't "the whole thing ran without me." Success is knowing where you belong in your own loop and being able to say why. If you finish this course and your time still goes into planning and reviewing — that's not your automation failing. That's your automation working.

    Three ways to move loops off your screen

    Background agents

    Kick off a loop and let it keep working while you do something else — write another ticket, review a different piece of code, or step away entirely. You come back to finished work instead of babysitting a progress bar.

    Remote or cloud agents

    Run the loop on a machine that isn't your laptop. This frees you from keeping your own machine on and open, and lets several loops run in parallel without competing for your local resources.

    Automated loops in CI

    Trigger a full Research → Plan → Implement → Validate pass automatically as part of your normal development pipeline — for example, on every pull request, using a continuous-integration platform. It isn't a new mechanism, either — it's the same unattended run, started by a repository event instead of by you.

    Notice what doesn't change: it's still the same core loop, following the same rules your context layer defines. What changes is where and when it runs, and whether a person has to be watching.

    A concrete example: the loop on every pull request

    Imagine a rule that says every pull request gets an automatic pass: the agent reads the diff, checks it against your project's rules, runs your tests, and leaves a review comment before a human ever opens the PR. That's the same Validate step you've been running by hand, just wired into your CI pipeline so it fires on its own trigger instead of a command you type.

    StageManual, at your keyboardAutomated in CI
    TriggerYou start itA pull request opens
    Where it runsYour machineA remote runner
    Who watchesYouNo one, until it reports back
    What runsThe core loopThe same core loop
    Why this matters This is the payoff of everything earlier in the course. A loop that only works when you personally drive it is a personal habit. A loop reliable enough to run unattended, on a schedule or a trigger, is a system — one that scales beyond one person at one keyboard.
    A caution Automation multiplies whatever you feed it, same as everything else in this course. A loop with weak rules or no real validation step will now produce weak results automatically and at scale. Get the loop right by hand first; automate it second.

    What you lose when nobody is watching

    Running unattended isn't your loop with the window closed. It's a different contract, and it takes away exactly three things. Each one has to be replaced by something you decide in advance, or something the run reports back.

    What you loseWhat has to replace it
    The prompt. Nobody is there to approve anything, so a step that wants permission just stops.Every permission decision made before the run — which is exactly what your standing-decisions log is, written as rules instead of judgment calls.
    Your ambient context layer. Unattended modes commonly load none of it by default — not your rules, your workflows, your specialists, your guardrails.You name what the run needs, one piece at a time. Nothing comes in unless you asked for it.
    Your eyes. You can't see it work, and prose output is no use to a script. A machine-readable result the next step can branch on, plus a report of what actually loaded and what it cost.

    Loss two is the one nobody expects, and it's also the most useful thing in this lesson. Because if your loop only works with your whole context layer auto-loaded, you don't actually know which parts of it were doing the work. Run it with nothing loaded, and whatever breaks is what was load-bearing. Everything that doesn't break was decoration you'd been paying for. That's the most honest audit your system will ever get, and the deliverable from it isn't the config — it's the list of things you turned out not to need.

    A guarantee that skips the unattended run was never a guarantee Guardrails are usually on that not-loaded-by-default list. If you wrote one as the check that always runs — the non-negotiable one — it is very likely not running in an unattended run, and failing silently. Worse, a run that lost half your system typically still reports success: same green tick, same exit status as a run that worked. So check what loaded and fail the run yourself when your own layer isn't there. An agent saying "done" is a claim; a green pipeline is a fact — and a green exit code is a claim again.

    Check yourself

    What actually changes when you move a core loop into a background or CI-triggered agent?

    Why should you get a loop working reliably by hand before automating it in CI?

    A step in your chain works 95% of the time. What happens when you chain ten of them?

    What are the three things an unattended run takes away from you?

    The one thing to remember

    Chains decay without warning, so keep the two ends and automate hard in between. Scaling isn't running the loop faster — it's running a loop you have checked, without you, while keeping the gates you deliberately decided to keep and writing down every one you remove.
